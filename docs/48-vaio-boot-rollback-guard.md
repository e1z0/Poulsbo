# VAIO Boot Rollback Guard

This note records the rollback-guard design that was added while the VAIO was
still unstable and later validated on real hardware.

The later healthy-boot hardware validation is documented in
[docs/55-vaio-rollback-guard-healthy-boot-validation.md](/root/Poulsbo/docs/55-vaio-rollback-guard-healthy-boot-validation.md).
The later failure-path auto-restore validation is documented in
[docs/56-vaio-rollback-guard-autorestore-validation.md](/root/Poulsbo/docs/56-vaio-rollback-guard-autorestore-validation.md).

## Why This Exists

[docs/46-sgx-dependency-slot-clear.md](/root/Poulsbo/docs/46-sgx-dependency-slot-clear.md)
captures the current problem: a risky override module can leave the target
reachable by ICMP but not usable over SSH after reboot.

The next useful improvement is to reduce the chance of getting stranded on the
next bad boot once the machine is recovered.

## Guard Model

Before a risky reboot, the guard script installs and arms a target-side systemd
service:

- service unit: `/etc/systemd/system/poulsbo-module-rollback.service`
- helper script: `/usr/local/sbin/poulsbo-module-rollback.sh`
- pending marker: `/var/lib/poulsbo-rollback/pending.env`
- previous-override backup: `/var/lib/poulsbo-rollback/gma500_gfx.previous.ko`

The validated unit shape is intentionally minimal:

- no explicit `After=multi-user.target`
- no explicit `Wants=multi-user.target`
- only `WantedBy=multi-user.target`

That is the form now generated by
[scripts/arm-vaio-gma500-rollback.sh](/root/Poulsbo/scripts/arm-vaio-gma500-rollback.sh)
and the form proven on the VAIO.

The boot-time helper:

- waits `ROLLBACK_GRACE_SECS` seconds
- exits immediately if the pending marker has been cleared
- otherwise restores the previous override from
  `/var/lib/poulsbo-rollback/gma500_gfx.previous.ko` when available
- otherwise removes `/lib/modules/<kernel>/updates/poulsbo/gma500_gfx.ko`
- runs `depmod -a`
- requests another reboot

That means a successful boot must be positively acknowledged from this
workstation. If post-boot health never reaches `overall=remote_usable`, the
guard stays armed and the target should eventually revert to the previous
known-good override when one exists, or to the stock module otherwise.

## Guarded Deploy Changes

[scripts/deploy-vaio-gma500-guarded.sh](/root/Poulsbo/scripts/deploy-vaio-gma500-guarded.sh)
now:

- arms the rollback guard before deploying when `AUTO_ROLLBACK_GUARD=1`
- preserves the currently installed override module as a rollback backup before
  replacing it
- clears the guard only after post-boot health returns to
  `overall=remote_usable`
- extends the post-reboot wait window to at least
  `ROLLBACK_GRACE_SECS + 180` seconds when the guard is enabled
- no longer exits early on `ssh_stalled_post_kex` while the rollback guard is
  active, because a later rollback reboot may still recover the machine

## Local Validation

Local checks passed:

- `bash -n scripts/arm-vaio-gma500-rollback.sh`
- `bash -n scripts/disarm-vaio-gma500-rollback.sh`
- `bash -n scripts/deploy-vaio-gma500-guarded.sh`

## Validation Status

This design is now validated on the VAIO in both major cases:

- healthy deploy/reboot with explicit confirmation:
  [docs/55-vaio-rollback-guard-healthy-boot-validation.md](/root/Poulsbo/docs/55-vaio-rollback-guard-healthy-boot-validation.md)
- unconfirmed boot with automatic restore of the previous override:
  [docs/56-vaio-rollback-guard-autorestore-validation.md](/root/Poulsbo/docs/56-vaio-rollback-guard-autorestore-validation.md)

The rollback guard is no longer waiting for first target-side proof. The
remaining work is narrower and future-facing:

1. keep using the guarded deploy path for risky module boots
2. preserve this validated service shape as the baseline
3. return focus to SGX render-path groundwork now that deploy recovery is real
