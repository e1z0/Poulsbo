# Poulsbo / GMA500 (SGX535) open-source acceleration driver — Sony Vaio

Reverse-engineered, open-source acceleration for the Intel GMA500 (Poulsbo US15W,
PowerVR SGX535, PCI 8086:8108, core rev 1.2.1) on a Sony Vaio (Ubuntu 18.04,
kernel 5.4.0-150 i686). Built on the mainline `gma500_gfx` DRM driver.

## What WORKS and is TESTED on the hardware

### 2D acceleration (SGX 2D BLIT core) — DELIVERED, 12/12 hardware tests
A `GMA_BLT_SUBMIT` DRM ioctl that drives the dedicated SGX 2D BLIT engine (slave
port at SGX+0x4000) with a strictly-validated command stream. Solid fills and
copies render on the GPU; a full test suite passes on the Vaio:

    12 passed, 0 failed
    PASS: fill submit
    PASS: fill readback (rect filled, border untouched)   <- real GPU pixels
    + 10 security/validation tests (bad handle, oversize stream, disallowed
      opcode, out-of-bounds reloc, reserved flags - all safely rejected)

Source: `features/blt-ioctl/` (kernel `blt_submit.c` + uapi `gma_blt_drm.h` +
`patch.diff`; userspace test `user/psb_blt_test.c`).
Build+run on target: `cd blttest && make && ./psb_blt_test`.

## What is FULLY REVERSE-ENGINEERED and EXECUTES on the hardware

### SGX535 3D microkernel bring-up — boots + runs command handlers
Hand-written kernel bring-up of Imagination's proprietary SGX microkernel
firmware (extracted from EMGD 1.18), with NO closed userspace:
- Boots to **INIT_COMPLETE** on real silicon (the microkernel's init handshake).
  Root cause of the long init hang was a USSE LIMM sibling-word corruption in the
  firmware relocation, fixed by splicing 8 const-size fields with the recovered
  `enc1530` encoder (bit-exact; reproduced the exact hang register value).
- **Host<->ukernel CCB command transport** works (commands consumed, ReadOffset
  advances, EDMTask steps per kick).
- **Command handlers execute real logic and return data**: the GETMISCINFO
  handler returns the true core revision `CoreRev=0x10201` (matches the HW
  CORE_REVISION register exactly) + CoreID, with the READY handshake - the first
  microkernel handler to run real logic and write back to the host.

RE artifacts: `features/sgx-3d-bringup/` - the driver (`sgx_3d.c`), the SGXInit
Ghidra decompilation, the extracted init-PDS programs, firmware headers, the
USSE handler disassemblies (`getmisc_handler_usse.txt`, `twod_handler_usse.txt`),
and the partial-but-working USSE + PDS instruction-set decode.

## The boundary (honest): microkernel *rendering* needs userspace materials
The microkernel render path (2D-via-USSE, TA/3D) requires a HW render-context +
per-context CCB payload + USSE/PDS *shader microcode* that are generated by the
closed EMGD userspace (`libpvr2d`/`libGLES`) - the kernel only *registers* a
userspace-built context (SGXRegisterHW2DContextKM). Those binaries are not
available (repo has only `libemgdsrv_init.so`; the Vaio has only Mesa). Proven
on hardware: the microkernel's `CMD_2D` handler does NOT drive the dedicated 2D
BLIT core (SOCIF FIFO stays empty for all VIRTUAL_FIFO/TWOD_REQ_BASE configs) -
it emits to the USSE pixel data master, which needs the userspace shader
pipeline. So microkernel-driven rendering is materials-gated; the delivered
working accelerated path is the direct 2D BLIT engine above.

## Toolchain
Build the module in an i386 Ubuntu-18.04 Docker against the Vaio kernel headers
(`docker/kbuild/`), scp to the Vaio, reboot to load (hot reload hangs the SoC).
Automated build/deploy/reboot-verify/test harness: `scripts/sgx3d_*.sh`.
